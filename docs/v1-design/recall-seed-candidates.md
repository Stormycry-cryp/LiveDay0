# 让当前 cue 找到旧经历

既定产品计划第三优先的第一小项：旧的重要经历按需进入召回。365/3650事件有界基线中，`old_unique_trip` 的来源能被全文检索发现，但两档召回均为空，因为发现的ID仅参与对最近48张卡的加分，旧规范事件从未进入候选。旧基线不改写为成功。

现在把已有全文/向量发现ID与有限近期ID汇合，再读取有效规范版本和来源。候选SQL同时校验tenant和active/provisional生命周期；按发现种子优先、同组valid_at DESC/id排列，共享单一`candidate_limit`（默认48），而非各自增加一份完整正文列表。同一规范身份只出现一次；来源、当前版本、unsafe排除、后续语义重排、完整卡缩短、分层编译和pinned cycle门禁保持原路径。未新增实体、存储、服务或检索提供者，也不会因为被检索而更改事件重要性或激活生活线程。

这是当前cue对旧经历的有限入口，不是“最新48张之外一律无效”的门槛。没有发现种子时仍使用有限近期候选；无足够相关内容时允许空历史。强cue返回规范事件及来源引用，不能把仅命中过去来源的文字当作当前事实。

单项`tests/test_recall_seed_candidates.py`先在新标记空私有PG/受限应用角色复现有效RED：全文找到旧ID、实际召回却漏掉。SQL小修后同一测试通过：83个本租户事件（另一个租户1个），旧事件、近期、无关、外租户、closed生命周期；来源引用存在；发现层注入外租户/关闭ID也不能越过规范SQL门禁；候选同ID去重、默认48及显式8上限。向量发现ID采用定向替身，只证明已发现ID能进入规范候选，**不代表真实pgvector质量或耗时通过**。两实例都停止、PID不存在；原RED日志保留。没有重跑旧演示、删除、重启、heldout/v3c或全仓测试。

性能文档中的旧召回耗时属于旧版本，不能用它推定新SQL的P95。本项验证候选数量，不证明数据库扫描、所有来源/增量、整个返回包或完整入口deadline已严格有界。英文固定cue的成功不能替代中文变体、重复事件、高连接节点和独立真人/真实模型质量验收；宽泛cue下全文排序及所有信号的联合最优排名也尚未验收。任务/快照自动清理与硬增长上限仍未实现。

后续回到第三优先尚未完成的产品门槛：核实完整返回包预算及deadline/工作量约束已有证据，选一个用户会遇到的具体反例推进，不追加泛化维护框架。
