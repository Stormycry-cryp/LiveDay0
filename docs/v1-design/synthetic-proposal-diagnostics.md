# 完整合成提案：语义差异与人工确认

2026-10-11。`synthetic_proposal_diagnostics.py` 仅认识两句固定合成爬山文字：改期后等待朋友确认、改期后朋友已经确认。先复用完整 ProposalBatch 和来源校验，再检查固定期望的原日期、新日期、主体及待确认状态。它按明确选择的合成样例比较精确值，不理解任意生活文字，也不改变默认提取或保存规则。

`CheckedSyntheticAdapter` 是显式套在已有 adapter 外的一小段接线：未知合成文字在调用 adapter 前拒绝；已验证响应仍有差异则抛出静态失败，阻止它到达现有 host 确认和写入。报告仅含固定字段路径、`date_mismatch`、`subject_mismatch`、`confirmation_mismatch` 等静态码，不返回期望值、错误值、引文或异常细节。没有新增诊断配置、模型判分、通用校验框架或数据库接口。

```sh
python3 -I -S -B tests/test_synthetic_proposal_diagnostics.py -v
```

8 项定向测试经实际 loopback GLMHTTP→完整合同→差异诊断→LocalMemorySession 运行：错原日期、错新日期、同为 user 但主体标识错误、待确认变已确认都在人工确认前阻止。两种正确结果可以进入现有 `save-sensitive` 确认；确认时尚未向服务提交，确认后才提交，拒绝则没有提交。真实终端确认函数以合成 TTY 替身验证 SAVE/拒绝。测试不启动数据库，MemoryService 是记录桩，回执中的 stored 只代表 host 调用了记录桩，不是 PostgreSQL 验收。

确认接线测试明确把合成来源标为 sensitive，从而复用已有确认流程；普通来源目前仍会直接保存，本批没有暗中让所有 capture 都需确认。固定正文同义改写也会判差异，诊断不是通用语义等价或真实模型正确性的保证。检查的字段限主体、卡片类型、目标背景、原日期、新日期、未完成未来和不确定状态；未检查的附加正文不因此获得真实性证明。
